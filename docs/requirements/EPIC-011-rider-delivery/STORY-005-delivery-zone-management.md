## Overview

This story covers the full CRUD lifecycle of delivery zones and the operational tools for managing the delivery network at the zone level. Admins can create, view, edit, and toggle zones via the Admin HQ; each zone is defined as a GeoJSON polygon with configurable base fee, per-km fee, SLA, surge pricing, and serviceability. The story also includes AI-driven rider rebalancing suggestions (demand forecast model recommends moving riders between overstretched and underpopulated zones), demand-vs-supply analytics, and surge pricing management. Customer addresses are matched to zones using point-in-polygon geospatial queries.

## Business Rules

| # | Rule |
|---|---|
| BR-001 | A **zone** is defined by a closed GeoJSON polygon (`GEOGRAPHY(POLYGON)` in PostGIS); all polygon coordinates must be in WGS84 (lat/lng). |
| BR-002 | A customer's delivery address is matched to a zone using `ST_Within(address_point, zone_polygon)`; if no zone matches, the address is not serviceable and checkout returns `ADDRESS_NOT_SERVICEABLE`. |
| BR-003 | **Delivery fee formula:** `fee = (base_fee + distance_km - per_km_fee) - surge_multiplier`. Free delivery if `order_value >= free_delivery_threshold`. |
| BR-004 | A zone marked `is_serviceable = false` stops accepting new orders from customers in that zone; existing active orders in the zone continue until completion. |
| BR-005 | **Surge pricing** is toggled per zone; when `is_surge_active = true`, the `surge_multiplier` (e.g., 1.5) is applied to the delivery fee formula. Surge never applies to the Rs 5 handling fee. |
| BR-006 | **Under strain** is computed as: `live_orders > (online_riders - 2)`; such zones are visually flagged and surface as rebalancing candidates. |
| BR-007 | **Rebalancing suggestions** are generated by a demand forecast model; the admin must explicitly `POST /admin/zones/rebalancing/:id/apply` to act on a suggestion. Applying a suggestion sends a push notification to the selected riders advising them to move to the target zone. |
| BR-008 | The demand-vs-supply endpoint returns hourly data for each zone for the past 7 days; it is read-only and used for planning. |
| BR-009 | Zone `min_order_value` gates checkout - customers whose cart total is below the zone minimum cannot proceed to checkout from that zone; error `ORDER_BELOW_MINIMUM` is returned. |

### POST /api/v1/admin/zones

**Auth:** `Bearer JWT` (admin_operations, admin_super)  
**Description:** Create a new delivery zone.

**Request Body:**
```json
{
  "zone_name": "Koramangala",
  "city": "Bengaluru",
  "polygon": {
    "type": "Polygon",
    "coordinates": [
      [
        [77.6100, 12.9200],
        [77.6400, 12.9200],
        [77.6400, 12.9450],
        [77.6100, 12.9450],
        [77.6100, 12.9200]
      ]
    ]
  },
  "base_fee": 25.00,
  "per_km_fee": 5.00,
  "sla_minutes": 30,
  "min_order_value": 50.00,
  "free_delivery_threshold": 199.00,
  "surge_multiplier": 1.5,
  "is_serviceable": true
}
```

**Response 201 Created:**
```json
{
  "success": true,
  "data": {
    "zone_id": "zone_uuid",
    "zone_name": "Koramangala",
    "city": "Bengaluru",
    "is_serviceable": true,
    "base_fee": 25.00,
    "per_km_fee": 5.00,
    "sla_minutes": 30,
    "min_order_value": 50.00,
    "free_delivery_threshold": 199.00,
    "surge_multiplier": 1.5,
    "is_surge_active": false,
    "area_sq_km": 7.2,
    "created_at": "2026-07-24T10:00:00Z"
  },
  "meta": {}
}
```

**Errors:**
| Code | HTTP | Meaning |
|---|---|---|
| `INVALID_POLYGON` | 422 | GeoJSON polygon not closed or < 3 vertices |
| `ZONE_NAME_DUPLICATE` | 409 | Zone name already exists in the same city |
| `INVALID_FEE` | 422 | base_fee or per_km_fee is negative |

| `is_serviceable` | BOOLEAN | No | Zone accepting new orders |
| `offline_reason` | TEXT | Yes | Why zone was taken offline |
| `created_by` | UUID | No | FK ? AdminUser |
| `created_at` | TIMESTAMPTZ | No | Creation timestamp |
| `updated_at` | TIMESTAMPTZ | No | Last update timestamp |

## Acceptance Criteria

| # | Criterion |
|---|---|
| AC-001 | Creating a zone with a valid GeoJSON polygon stores it in PostGIS and returns zone_id; the zone is immediately available for address matching. |
| AC-002 | A customer checkout with a delivery address outside all zone polygons returns `ADDRESS_NOT_SERVICEABLE`. |
| AC-003 | Setting `is_serviceable = false` blocks new checkouts from that zone; existing IN_PROGRESS orders are unaffected. |
| AC-004 | Surge toggle `is_surge_active = true` with multiplier 1.5 causes the fee-estimate endpoint to return `delivery_fee = (base + distance) - 1.5`. |
| AC-005 | Zone list summary chips (`serviceable_zones`, `zones_under_strain`, `avg_delivery_minutes`) reflect live data. |
| AC-006 | A zone with `live_orders > online_riders - 2` shows `coverage_status = UNDER_STRAIN` in the zone list. |
| AC-007 | Applying a rebalancing suggestion sends a push notification to each recommended rider and updates suggestion status to `APPLIED`. |
| AC-008 | Creating a zone with a duplicate name in the same city returns HTTP 409 `ZONE_NAME_DUPLICATE`. |

## Notes

- Polygon coordinates in the `POST /admin/zones` request follow GeoJSON `[lng, lat]` convention (longitude first), matching the GeoJSON spec; the `POST /admin/geofences` endpoint in STORY-004 uses `[lat, lng]` convention for legacy reasons. This discrepancy should be standardised in v2 - document in API changelog.
- The `coverage_status` field is computed at query time from live Redis data; it is not persisted in the database.
- Rebalancing suggestions expire 2 hours after generation; the Automation Engine (EPIC-015) can be configured to auto-generate suggestions on a schedule.
